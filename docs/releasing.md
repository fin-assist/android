# Подготовка версии Android

Владелец создаёт `release/X.Y.Z` из актуального `main`. Если ветка создана без повышения версии,
первый push запускает CI с номером прошлого выпуска и ожидаемо падает на проверке соответствия
`appVersionName` имени релизной ветки (FIN-377).

Первым изменением подготовить отдельный PR в новую релизную ветку: обновить `appVersionName`
в `app/build.gradle.kts` до `X.Y.Z`, пройти проверки и ревью. Остальные PR в эту ветку ждут, пока
владелец сольёт PR версии; затем они включают это изменение из актуальной базы. Это обычный
процесс PR без прямой записи в защищённую релизную ветку и без отключения проверки версии.
После слияния выпуска `main` сохраняет эту версию до подготовки следующего.
Исправление FIN-377 выравнивает оставшуюся `0.2.8` с новым выпуском `0.2.15` после выпуска `0.2.14`.

Это одна исходная версия для `android.defaultConfig.versionName` и `BuildConfig.CLIENT_VERSION_NAME`.
В Android-версии flavors `mock`/`local` добавляют `-mock`/`-local`; заголовок `X-Client-Version` всегда
использует версию без этих суффиксов: например, `android/0.2.15+41`. `AppModule.clientVersion()` передаёт
`CLIENT_VERSION_NAME` и `VERSION_CODE` в общий `ClientVersion`; заголовок устанавливает сетевой interceptor.

`PF_VERSION_CODE` — отдельный монотонно растущий номер публикуемой сборки, а не номер релизной ветки.
При изменении `appVersionName` его не заменять и не уменьшать. Существующие значения по умолчанию
(`GITHUB_RUN_NUMBER` в CI, `1` локально) не гарантируют монотонность между разными workflows и повторными
запусками; перед публикацией номер задаёт процесс выпуска.

CI проверяет соответствие `appVersionName` любой `release/X.Y.Z` в контексте запуска: push в релизную
ветку, PR в неё и PR из неё в `main`. Для обычного PR в `main` проверяется формат исходной версии;
произвольное имя рабочей ветки версию не задаёт. Проверка не обращается к GitHub API и не вычисляет
версию из номера CI-прогона. Локально:

```sh
GITHUB_REF_NAME=release/0.2.15 python3 scripts/check-app-version.py
```

Задание сборки дополнительно проверяет полученные manifest и `BuildConfig.java` для `mockDebug`,
`localDebug` и `prodRelease`: Android-версия содержит только ожидаемый flavor-суффикс, клиентская —
исходную версию без суффикса. Регрессионные тесты проверки — `scripts/test_check_app_version.py`.
Передача версии в обычные HTTP-запросы и SSE покрыта `ServiceGateNetworkTest`.

Правила выбора целевой ветки PR и слияния владельцем остаются в `AGENTS.md`, раздел Workflow.
Изменение номера сборки не добавляет пользовательский сценарий и не требует UI-прогона.
